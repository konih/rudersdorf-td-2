## Decisions taken inside the task

Each is a German comment or docstring at the place named.

1. **Object created before its capability opened** answers through the stand-in from then on;
   the stand-in object is built once, lazily, with the constructor arguments of the original
   (`Werkstueck._aktives`). Real and stand-in rules never mix, as for functions.
2. **`wartet_auf`** lists the `braucht` missions whose capability is open now; a capability
   that is open by itself waits for nothing (`Werkbank.wartet_auf`). So `bot` with `wegfindung`
   forced open gives `[2, 3, 4, 5]` (`bauregel` is open too), with `strategien` forced open `[7]`.
3. **`waehle_paket(False)`** is always `"werkstatt"`; with `None` only the exact value `1`
   selects the reference (`waehle_paket`).
4. **Syntax error**: the `Lernfehler` carries the file and line of the syntax error, kind and
   message from the `SyntaxError`; capability and mission are `None`, because the whole file is
   unreadable (`Werkbank._lernfehler_beim_laden`). Whoever shows it must cope with `None`.
5. **`strategien()`**: the entries of the workshop's `STRATEGIEN` when solved,
   `{"zufall": stand-in}` when open (`Werkbank.strategien`). Each entry is wrapped so that a call
   is handled like `rufe` (`NochOffen` → open and the `zufall` stand-in answers; other errors →
   `Lernfehler`; an own strategy counts for mission 8). Plan, Constitution Check II: "every
   engine call into the workshop goes through `Werkbank`". `functools.wraps` keeps the original
   reachable, so `inspect` still finds its file and first line (the plan's `Rückgabewert` error).
6. **Missing stand-in**: `RuntimeError` naming the capability, from `ersatz.ersatz_fuer`; an
   engine bug, not a learner error. `erzeuge` looks the class up at once when it needs it.
7. **Import errors at construction** raise `Lernfehler` from the constructor (not asked by a
   test of T004): a workshop that cannot be imported cannot be played; FR-026 wants the error shown.
8. **Construction uses Python's normal import; only `lade_neu` loads fresh.** A fresh load drops
   the package's modules from `sys.modules` and imports them again (new module objects, so deleted
   names vanish and a failure half-way cannot damage the old modules); on failure the old ones
   are put back. Constructing a second workbench does not re-execute the modules, so objects
   that tests imported directly keep their classes.
9. **A name outside the registry** passed to `rufe` or `erzeuge` is a `RuntimeError`.
10. **`STRATEGIEN` that is not a dictionary** is a `Lernfehler` for mission 7 (line 0).
11. **Probe order for `Zauber`**: `wirke` last, because the solved base class raises
    `NotImplementedError` there, which ends that probe.

## Harness gaps

- The method signatures used by the class probes (`tick`, `aktualisiere`, `wirke`, …) are only
  checked up to the constructor, because every constructor of the shipped workshop raises
  `NochOffen`. A wrong method call in a probe would raise `TypeError`, be ignored, and the
  capability would be noticed as open only at its first call in play. Deferred to T011 and T026
  (the references of tracks C and D): "a solved package has nothing open" then exercises them;
  T046 runs every capability.
- Objects the learner's own code creates (mission 20 puts `Brand(...)` into `gegner.effekte`)
  are not wrapped by `erzeuge`. The engine task that ticks effects (T015, tests in T014) decides how those
  calls reach `Werkbank.versuche`. Not a claim of this task.
- A late `NochOffen` raised by another capability's function that the learner's code calls
  directly (`magie` calling `.horde.fuege_effekt_hinzu`) marks the calling capability as open by
  itself; its label then says "open" instead of "waits for". Rare (the probe normally sees it
  first) and harmless for play; recorded, not fixed.

## Learnings

Class: tooling, guidance.

- tooling · Two legs launched side by side must not share an output directory: the launcher
  calls its single leg `reviewer-a` and replaces reviewer A's file. Give the paid leg its own
  directory, or run it after reviewer A and rename. → loop.md *Lessons*.
- guidance · Code that reloads Python modules has three places to clear (`sys.modules`, the
  attribute on the parent package, the cached byte-code) and two paths that must both clear them
  (fresh load and roll-back after a failure); reviewer A tests each. → loop.md *Lessons*.
- guidance · A wrapper that forwards attribute access must treat the look-up itself as learner
  code, not only the call. → loop.md *Lessons*.
- guidance · New tests that are green at the first run need the mutation run before the review:
  it found two missing cases here. → loop.md *Lessons*.
