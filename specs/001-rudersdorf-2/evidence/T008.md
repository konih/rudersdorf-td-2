## Decisions taken inside the task

- **Mission 8 judges one entry.** `setUp` raises `NochOffen("Mission 8: Deine eigene Strategie")`
  while `STRATEGIEN` is not a dictionary with a key beyond the five standard ones. Otherwise the
  four tests look at the first own entry that meets the whole rule, or, if none does, at the
  first own entry. That is the contract's "at least one more key whose function follows …": a
  copy, a broken or a still-open entry beside a good one does not fail the mission (controls
  G01, G02, G07, G08). If the only own entries raise `NochOffen`, the tests report "still open".
  "Differs" is identity of the chosen enemy; the four test lists vary `rest_weg`, `leben`,
  `max_leben`, position, `fliegt` and `ist_boss`, so rules built on any of them can differ.
- **`STRATEGIEN` test.** The identity check alone is already true on the stubs; the same test then
  calls every rule through the table, so it is red until mission 7 is solved.
- **Stand-in shapes** follow `rudersdorf/ersatz.py` and are fetched with `ersatz_fuer`, after an
  assertion that the entry exists (so a missing stand-in is a failure with a message, not a
  `RuntimeError`). What the
  tests fix for T009:
  - `reichweite`: `in_reichweite(position, reichweite, gegner)` → a new list, in list order, of
    the enemies within `reichweite` (Euclidean) whose cell row (`y // 40`) or cell column
    (`x // 40`) is the one of `position`.
  - `strategien`: `ERSATZ["strategien"]` has exactly the key `zufall` (the key the workbench asks
    for); `zufall(kandidaten, turm)` returns one of the candidates, `None` for an empty list,
    leaves the list alone, and over 200 calls on slowly advancing enemies picks at least two
    different ones.
  - `kettenblitz`: always a fresh `[start]`.
  - `ausbau`: `wende_ausbau_an(werte, ausbau)` answers `None` for every upgrade, valid or not, and
    leaves `werte` alone. This is the one reading of "reports that upgrades are unavailable" a
    function with the workshop's arguments can express without returning improved values; the
    engine is expected to treat `None` as "cannot be upgraded" (believed: T015 is not written yet).
- **Not asserted, because the spec set leaves it open:** where the random stand-in takes its
  randomness from (plan.md wants all randomness from the match's own generator; control G05 shows
  the test also accepts a choice derived from the enemies' state); whether the `reichweite`
  stand-in filters defeated enemies; what `wende_ausbau_an` does with a value that is not a pair.
- **Beyond the task's list, from the contract's conventions:** `kettenblitz` deals no damage itself
  ("returns the hit order"; arguments are not modified); `staerkster`/`schwaechster` read `leben`,
  not `max_leben`; `naechster` and both range checks are Euclidean.

## Learnings

Class: guidance (persisted as lines in loop.md, *Lessons*).

- A test that picks "the entry to judge" among several learner entries must treat every failure
  of an entry, `NochOffen` included, as "not this one"; only an empty selection reports "still
  open".
- The contract's general conventions (arguments not modified, ties to the earlier) apply to every
  mission, also where the mission's own rule lists what "solved" means; write the case.
- Stand-in tests assert that the registry entry exists before fetching it, so their red is an
  assertion as the task's *Verify* line asks, not a `RuntimeError`.
